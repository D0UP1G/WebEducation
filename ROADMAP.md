# WebEducation — роадмап

Цель: собрать к защите один полностью работающий путь «администратор публикует
курс → ученик проходит и сдаёт → автоматическая/ручная проверка → прогресс»,
а затем расширять его без разрушения архитектуры.

Актуальный срез: `develop` после PR #45. Составная сдача, педагогические типы
всех 30 шагов, серверные требования к ручным доказательствам и подсказка Scratch
после неверного ответа доступны. PR #44 уточнил рабочие экраны дизайна. Состояние этапов и
требования полученных [материалов организатора](docs/organizer/README.md) приведены в
[сверке](docs/current-gap-analysis.md). [Текущий план четырёх агентов](docs/team-work-plan.md)
содержит владельцев и критерии готовности. Этот документ сохраняет исходный
порядок этапов, включая уже выполненные пункты.

Так как проект сейчас ведёт один агент, критический порядок сокращён до
[плана стенда на одном хосте](docs/single-agent-demo-plan.md): Compose → runner →
сквозной E2E → Cloudflare Tunnel → release. Импорт 3/9/30 и P1 выполняются после
защищённого Python-сценария.

DEV-1-инфраструктура этапа 5 уже реализована в `develop`: request-id-логи,
лимиты upload на Nginx и API, проверка форматов, backup/restore runbook,
контрактный `413 file_too_large` и опциональный HTTPS Compose-профиль. Для этой
части остаются стендовые проверки; Docker daemon на текущей машине недоступен,
публичный HTTPS-хост не подтверждён.

В интеграционной ветке CI дополнительно запускает `preflight_curriculum_import`
и проверяет оба Compose-профиля через `docker compose config`; это контроль
целостности карты и конфигурации, а не запись учебного пакета в базу.

После получения пакета добавлены P0-задачи: представить 3 курса / 9 модулей /
30 шагов без потери структуры, перенести содержание в БД и применить официальный
брендбук. Команда дополнительно потребовала защищённый официальный зачёт Python:
локальный запуск оставить для самопроверки, официальный код повторно выполнять
в изолированной серверной среде. Текущий браузерный протокол этого не делает.

Для переноса пакета DEV-4 подготовил карту 3 курсов, 9 модулей и 30 шагов с
привязкой к SHA-256 исходника, разделением ученических и проверочных данных и
сохранением многострочных Python-входов. PR #37 добавил к шести ручным шагам
`required_evidence`; приватные `curator_criteria` импортируются в
`content.review_criteria` без выдачи ученику. [Контракт импорта](docs/organizer/import-contract.md)
задаёт преобразование каждого типа и фиксирует блокеры. Сам импорт ожидает модель
модулей, поля паспорта и ключ импорта от DEV-1.
Владелец утвердил 24.09.2026 по 1 баллу за каждый из 30 шагов; решение внесено
в карту в PR #40.

## Приоритеты

`P0` — без этого не проходит основной сценарий защиты. `P1` — усиливает продукт
после ядра. `P2` — только если остаётся время.

## Этап 0. Согласование и каркас (P0)

- Зафиксировать `docs/api-contract.md`, формат ошибок, роли и статусы.
- Назначить владельца React/TypeScript; если владельца нет — переключиться на
  Django templates и не поддерживать два рендера.
- Создать Django-проект и приложения: `accounts`, `courses`, `learning`,
  `grading`, `mentoring`, `progress`.
- Поднять Docker Compose: web/API, PostgreSQL и reverse proxy.
- Добавить `.env.example`, healthcheck, миграции и синтетические demo-accounts.
- Сделать smoke-тест запуска и `README` с одной командой старта.

Результат: пустой, но запускаемый стенд и согласованный контракт.

## Этап 1. Данные и авторизация (P0)

- Кастомный `User` с ролью и безопасными синтетическими credentials.
- `Course`, `CourseRevision`, `StepRevision`, `Enrollment`.
- Правило: published revision неизменяема; enrollment хранит конкретную версию.
- По решению владельца от 24.09 при публикации требовать теорию и хотя бы один
  контрольный вопрос, как в §04 кейса; обновить API, тесты и подсказки редактора.
- Сессионный login/logout/me, CSRF и DRF permissions.
- Админские CRUD для draft курса и упорядочивания шагов.

Результат: администратор может собрать курс, но ещё не все шаги проходят.

## Этап 2. Расширяемые шаги и прохождение (P0)

- Реестр типов шага с `type_key`, `schema_version`, валидатором и обработчиком.
- Реализовать типы пакета по [карте 30 шагов](docs/organizer-step-map.md):
  `theory`, `quiz.single_choice`, `quiz.multiple_choice`, `answer.exact`,
  `scratch.numeric_answer`, `algorithm.python`, `artifact.scratch`,
  `artifact.minecraft`, `artifact.project`.
- Добавить `Submission` и единые правила повторной сдачи.
- Студенческие экраны: назначенные курсы, шаг, сдача, статус и история;
  завершение теории через действие `complete`.
- Не отдавать браузеру правильные ответы через API. Исторический браузерный
  Python получает входы тестов по подписанному заданию; оригинальный учебный
  DOCX в публичном Git содержит ответы и эталонные решения. Для защищённого
  зачёта нужны дополнительные серверные тесты и исполнение присланного кода.

Результат: ученик проходит курс и может отправить все обязательные для демо типы.

## Этап 3. Проверки (P0)

- Автоматические ответы проверять серверным обработчиком.
- Для числового Scratch из пакета сохранять подсказку в закрытом содержимом
  шага и выдавать в `feedback` только после неверной сдачи. Контракт и API-тест
  добавлены DEV-3; импортированный курс ещё требует сквозной проверки DEV-4.
- Web Worker оставить для локальной самопроверки. Официальную Python-сдачу
  запускать изолированно на сервере с лимитами ресурсов; сервер сам вычисляет
  статус и баллы. До реализации действует исторический браузерный протокол с
  ограничениями доверия из `docs/dev3-handoff.md`.
- Работы Scratch/Minecraft сохранять как файл, ссылку и пояснение в одной
  попытке, когда этого требует шаг, и отправлять куратору. Серверная часть
  составной сдачи в `develop` готова. Карта DEV-4 задаёт обязательные поля;
  правила PR #36 проверены; DEV-2 подключает поля редактора и формы ученика.
- Реализовать `pending_review`, `accepted`, `incorrect`, `returned`, `error` и
  polling ручной проверки из фронтенда. `queued` и `checking` остаются
  зарезервированными состояниями модели для будущей асинхронной проверки.
  `incorrect` — неверное решение, `error` — технический сбой проверки.

Результат: ученик сразу получает авто-результат или понятное ожидание куратора.

## Этап 4. Куратор и прогресс (P0)

- Очередь ручных проверок только для закреплённых учеников.
- Принять/вернуть с обязательным комментарием при возврате.
- Вопросы строго в контексте шага, без общего чата.
- Прогресс из принятых сдач; баллы за авто- и ручную проверку равноправны.
- Экран куратора с объяснимыми сигналами: 72 часа без зачёта, две неверные
  попытки на одном шаге за 24 часа, возврат без пересдачи 24 часа.
- Экран ученика с `next_action`, процентом завершённых шагов, рейтингом по
  баллам и разбивкой баллов по шагам.

Результат: полностью демонстрируемый end-to-end сценарий кейса.

## Этап 5. Демо, тестирование и стенд (P0)

- Seed синтетического курса с поддерживаемыми типами шагов и трёх
  ролей; импортировать полученный пакет организатора (3 курса, 9 модулей,
  30 шагов) без изменения исходного DOCX.
- E2E smoke: publish → assign → локальная самопроверка Python → официальный
  серверный результат → ручной возврат → пересдача → принятие → прогресс.
  Поддельный вывод браузера не должен давать зачёт.
- Тесты permissions: ученик не видит чужую сдачу, куратор — чужих учеников,
  ученик — скрытые ответы/тесты.
- Тесты versioning: новая публикация не меняет старое enrollment и попытки.
- Логи с `request_id`, понятные ошибки, лимиты upload и проверка файлов.
- Развёртывание на VPS/согласованном хосте по HTTPS; проверить восстановление
  базы и persistent volume.
- Дополнить README проверенной командой запуска, demo-accounts, URL стенда и
  тем, что не успели.
- Проверить перед стоп-кодом 26 сентября 09:00, что в `main` есть рабочий код,
  README и MIT `LICENSE`, а на стенде используются только синтетические данные.

Результат: защита открывается по ссылке и повторяется по короткому сценарию.

## Этап 6. После ядра (P1)

- Версионирование схем типов и миграция старых `content` при необходимости.
- Фильтры/поиск в очереди куратора и CSV-отчёт по прогрессу.
- Улучшение редактора курса и предпросмотр опубликованной версии.
- Наблюдаемость браузерного запуска: ошибки загрузки Pyodide и таймауты.

## Этап 7. Не брать до готовности P0 (P2)

- Встроенные Scratch/Minecraft-редакторы.
- WebSocket-уведомления вместо polling.
- Сложный рейтинг, геймификация и лидерборды.
- Платежи, CRM, расписание, общий мессенджер, видеосвязь и продуктовый AI.

## Критерий готовности к защите

Стенд считается готовым, когда новый зритель может без ручного вмешательства
пройти демонстрационный сценарий из `docs/case-alignment.md`, а
команда может объяснить, где находятся границы ролей, почему опубликованные
версии неизменяемы и чем локальная самопроверка Python отличается от
официального зачёта, вычисленного сервером.

## Риски и решения

| Риск | Решение |
|---|---|
| Разъезд API и React при параллельной работе | Подключать готовые маршруты уже сейчас; новые поля и статусы брать из одного API-контракта после PR в develop |
| Браузерная оценка не защищена от подделки | Локальный запуск использовать для самопроверки; официальный код проверять изолированно на сервере. До этого не заявлять защищённый зачёт |
| Материалы организатора ещё не перенесены в продукт | Модульная структура и импорт 3/9/30 из полученного пакета, проверка всех типов |
| Конфликт миграций | Один владелец миграций; остальные PR не меняют миграции без согласования |
| Срыв времени | Заморозить P0, убрать P1/P2 и сохранить рабочий демо-сценарий |
| Рабочий UI требует стендовой сверки с официальным брендбуком | Проверить токены, статусы и все три роли после PR #34 на целевом стенде |
