# WebEducation — роадмап

Цель: собрать к защите один полностью работающий путь «администратор публикует
курс → ученик проходит и сдаёт → автоматическая/ручная проверка → прогресс»,
а затем расширять его без разрушения архитектуры.

Состояние этапов по текущему `develop` и оставшаяся приёмка приведены в
[сверке с кейсом](docs/case-alignment.md). Этот документ сохраняет порядок
приоритетов, включая уже выполненные пункты.

## Приоритеты

`P0` — без этого не проходит основной сценарий защиты. `P1` — усиливает продукт
после ядра. `P2` — только если остаётся время.

## Этап 0. Согласование и каркас (P0)

- Зафиксировать `docs/api-contract.md`, формат ошибок, роли и статусы.
- Назначить владельца React/TypeScript; если владельца нет — переключиться на
  Django templates и не поддерживать два рендера.
- Создать Django-проект и приложения: `accounts`, `courses`, `learning`,
  `grading`, `mentoring`, `progress`.
- Поднять Docker Compose: web/API, PostgreSQL и reverse proxy.
- Добавить `.env.example`, healthcheck, миграции и синтетические demo-accounts.
- Сделать smoke-тест запуска и `README` с одной командой старта.

Результат: пустой, но запускаемый стенд и согласованный контракт.

## Этап 1. Данные и авторизация (P0)

- Кастомный `User` с ролью и безопасными синтетическими credentials.
- `Course`, `CourseRevision`, `StepRevision`, `Enrollment`.
- Правило: published revision неизменяема; enrollment хранит конкретную версию.
- Сессионный login/logout/me, CSRF и DRF permissions.
- Админские CRUD для draft курса и упорядочивания шагов.

Результат: администратор может собрать курс, но ещё не все шаги проходят.

## Этап 2. Расширяемые шаги и прохождение (P0)

- Реестр типов шага с `type_key`, `schema_version`, валидатором и обработчиком.
- Реализовать минимум: `theory`, `quiz.single_choice`, `answer.exact`,
  `algorithm.python`, `artifact.scratch`, `artifact.minecraft`.
- Добавить `Submission` и единые правила повторной сдачи.
- Студенческие экраны: назначенные курсы, шаг, сдача, статус и история;
  завершение теории через действие `complete`.
- Не отдавать браузеру правильные ответы. Для браузерного Python входы тестов
  выдаются ученику по подписанному заданию; сервер сохраняет ожидаемый вывод.

Результат: ученик проходит курс и может отправить все обязательные для демо типы.

## Этап 3. Проверки (P0)

- Автоматические ответы проверять серверным обработчиком.
- Python-код запускать в браузерном Web Worker; сервер сверяет полученный
  вывод с ожидаемыми ответами. Границы доверия описаны в `docs/dev3-handoff.md`.
- Работы Scratch/Minecraft сохранять как ссылку или файл и отправлять в очередь
  ручной проверки.
- Реализовать `pending_review`, `accepted`, `incorrect`, `returned`, `error` и
  polling ручной проверки из фронтенда. `queued` и `checking` остаются
  зарезервированными состояниями модели для будущей асинхронной проверки.
  `incorrect` — неверное решение, `error` — технический сбой проверки.

Результат: ученик сразу получает авто-результат или понятное ожидание куратора.

## Этап 4. Куратор и прогресс (P0)

- Очередь ручных проверок только для закреплённых учеников.
- Принять/вернуть с обязательным комментарием при возврате.
- Вопросы строго в контексте шага, без общего чата.
- Прогресс из принятых сдач; баллы за авто- и ручную проверку равноправны.
- Экран куратора с объяснимыми сигналами: 72 часа без зачёта, две неверные
  попытки на одном шаге за 24 часа, возврат без пересдачи 24 часа.
- Экран ученика с `next_action`, процентом завершённых шагов, рейтингом по
  баллам и разбивкой баллов по шагам.

Результат: полностью демонстрируемый end-to-end сценарий кейса.

## Этап 5. Демо, тестирование и стенд (P0)

- Seed синтетического курса со всеми шестью обязательными типами шагов и трёх
  ролей; после получения учебного пакета — импорт разрешённых материалов.
- E2E smoke: publish → assign → browser Python result → manual return →
  resubmit → accept → progress.
- Тесты permissions: ученик не видит чужую сдачу, куратор — чужих учеников,
  ученик — скрытые ответы/тесты.
- Тесты versioning: новая публикация не меняет старое enrollment и попытки.
- Логи с `request_id`, понятные ошибки, лимиты upload и проверка файлов.
- Развёртывание на VPS/согласованном хосте по HTTPS; проверить восстановление
  базы и persistent volume.
- Дополнить README проверенной командой запуска, demo-accounts, URL стенда и
  тем, что не успели.

Результат: защита открывается по ссылке и повторяется по короткому сценарию.

## Этап 6. После ядра (P1)

- Версионирование схем типов и миграция старых `content` при необходимости.
- Фильтры/поиск в очереди куратора и CSV-отчёт по прогрессу.
- Улучшение редактора курса и предпросмотр опубликованной версии.
- Наблюдаемость браузерного запуска: ошибки загрузки Pyodide и таймауты.

## Этап 7. Не брать до готовности P0 (P2)

- Встроенные Scratch/Minecraft-редакторы.
- WebSocket-уведомления вместо polling.
- Сложный рейтинг, геймификация и лидерборды.
- Платежи, CRM, расписание, общий мессенджер, видеосвязь и продуктовый AI.

## Критерий готовности к защите

Стенд считается готовым, когда новый зритель может без ручного вмешательства
пройти демонстрационный сценарий из `docs/case-alignment.md`, а
команда может объяснить, где находятся границы ролей, почему опубликованные
версии неизменяемы и где проходит граница доверия браузерной проверки кода.

## Риски и решения

| Риск | Решение |
|---|---|
| Нет владельца фронтенда | Немедленно выбрать React-владельца или перейти на templates |
| Браузерная оценка не защищена от подделки | Явно использовать её для учебного MVP; при требовании защищённого зачёта добавить серверный runner |
| Нет материалов организаторов | Использовать синтетический курс и явно пометить допущение |
| Конфликт миграций | Один владелец миграций; остальные PR не меняют миграции без согласования |
| Срыв времени | Заморозить P0, убрать P1/P2 и сохранить рабочий демо-сценарий |
| Нет официального брендбука/учебного пакета | Не выдавать черновик за официальный; использовать синтетический курс и запросить материалы у организатора |
