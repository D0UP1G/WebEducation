# WebEducation

Проект образовательной платформы для самостоятельной подготовки школьников 1–9 классов по спортивному программированию. Основание — [кейс хакатона](keys-obrazovatelnaya-platforma.pdf) Федерации спортивного программирования Чувашской Республики.

## Текущее состояние

В `develop` объединены ядро DEV-1, React-клиент DEV-2 и модули DEV-3:
вход и кабинеты трёх ролей, редактор курса, девять типов шагов, сдачи,
ручная проверка, вопросы и прогресс. PR #50 добавил изолированную серверную
проверку Python; Pyodide в браузере используется для самопроверки по открытому
примеру. После зачёта ученик может отправлять новые варианты кода, и каждый
проверяется сервером, сохраняя прежний зачёт и баллы.

PR #51 добавил паспорт курса, неизменяемую структуру модулей и импорт
официального пакета: три курса, девять модулей, 30 шагов. `seed_demo` публикует
только эти курсы, создаёт три синтетические учётные записи и назначает ученика
на все три курса. Повторный импорт не создаёт новых ревизий без изменений.
Локальный Compose-прогон Python прошёл. Публичный HTTPS-стенд и
полный сценарий трёх ролей ещё требуют приёмки. Актуальные задачи — в
[аудите от 25.09](docs/case-compliance-and-task-plan-2026-09-25.md).

Кейс требует работающие контуры **ученика, куратора и администратора**, разнотипные шаги (теория, контрольный вопрос, задача с точным ответом, Scratch, Minecraft Education, алгоритмическая задача с тестами), автоматическую и ручную проверку, объяснимый прогресс и рейтинг. Точный перечень выполненного, недостающего и критерии приёмки — в [сверке с кейсом](docs/case-alignment.md).

## Быстрый запуск

```bash
cp .env.example .env
docker compose up --build -d
docker compose exec web python manage.py seed_demo
```

Локальный `.env.example` привязывает прокси к `127.0.0.1:8080`, поэтому
стенд не доступен с других компьютеров без явного изменения `PROXY_PORT` или
настройки туннеля. API после healthcheck доступен на
`http://localhost:8080/api/v1/`, проверка:

```bash
curl http://localhost:8080/api/v1/health
```

Корень `/` отдаёт собранный React-клиент, а `/api/v1/` проксируется в Django.
Локальная самопроверка Python выполняется в браузере через Pyodide.
Официальная сдача исполняется в отдельном `runner`-контейнере без сети и
доступа к БД; `web` обращается к нему по Unix-сокету.

## Демо-данные

Команда `seed_demo` повторно импортирует официальные курсы и создаёт три
синтетические учётные записи с чистыми назначениями. Она не добавляет
синтетический курс, попытки, вопросы или проверки куратора. Повторный запуск
не дублирует курсы, модули, шаги и назначения. Пароль у всех демо-аккаунтов —
`demo`.

| Роль | Логин | Что можно проверить |
| --- | --- | --- |
| Администратор | `admin_demo` | три официальных курса и управление ими |
| Куратор | `curator_demo` | чистая очередь ручной проверки для новых сдач ученика |
| Ученик | `student_demo` | все три официальных курса без заранее созданных попыток |

Размер файла проверяется дважды: Nginx отклоняет тело запроса свыше
`CLIENT_MAX_BODY_SIZE` (по умолчанию `11m`), а Django применяет точный лимит
`MAX_UPLOAD_SIZE` к самому файлу (по умолчанию 10 MiB). Прокси-лимит должен
оставаться немного выше, чтобы multipart-оболочка не отклонила допустимый файл.

Для HTTPS используется отдельный Compose-профиль с сертификатом и ключом вне
репозитория. Задайте пути к PEM-файлам и запустите профиль на хосте с доменом:

```bash
TLS_CERTIFICATE_FILE=/etc/letsencrypt/live/example/fullchain.pem \
TLS_CERTIFICATE_KEY_FILE=/etc/letsencrypt/live/example/privkey.pem \
docker compose -f docker-compose.yml -f docker-compose.https.yml up --build -d
```

Профиль проверяет наличие обоих файлов до старта Nginx, перенаправляет HTTP на
HTTPS и проксирует API уже с `X-Forwarded-Proto=https`. Сертификаты и ключи не
копируются в образ и не добавляются в Git. HTTPS-профиль принудительно выключает
`DJANGO_DEBUG` и включает `Secure` для сессионного и CSRF cookie. Перед публичным
запуском замените в `.env` примерный `DJANGO_SECRET_KEY` на длинное случайное
значение, задайте уникальные `POSTGRES_PASSWORD` и `DATABASE_URL` с тем же
паролем, укажите домен в `DJANGO_ALLOWED_HOSTS`, а адрес вида
`https://ваш-домен` — в `DJANGO_CSRF_TRUSTED_ORIGINS`. Backend откажется
стартовать без настоящего ключа при выключенном debug. HTTPS-профиль также
требует явных `DATABASE_URL`, `POSTGRES_PASSWORD`, домен и HTTPS-origin; при
примерном пароле БД, коротком/примерном ключе или локальном домене запуск
останавливается до миграций. Сгенерируйте случайный ключ длиной не менее 50
символов и уникальный пароль БД, не храните их в Git. Учитывайте, что
`seed_demo` создаёт известные пароли `demo`: публичный стенд должен содержать
только синтетические аккаунты и назначения, не использоваться для реальных
учеников и получать учебный контент из официального пакета.

## Резервная копия и восстановление БД и файлов

Для согласованной пары PostgreSQL + загруженные работы сначала остановите запись,
затем создайте оба файла с одинаковой меткой времени:

```bash
docker compose stop proxy web
./scripts/backup-instance.sh
docker compose up -d web proxy
```

В `backups/` появятся `webeducation-<метка>.dump` и
`webeducation-<метка>.media.zip` (папка исключена из Git). ZIP не содержит
пользователей БД, но может содержать работы учащихся: защищайте обе копии как
чувствительные данные. Проверяйте восстановление **на копии стенда**, после
остановки `web` и `proxy`; оно заменяет текущую БД и media:

```bash
docker compose stop web proxy
CONFIRM_RESTORE=1 ./scripts/restore-db.sh backups/webeducation-YYYYMMDDTHHMMSSZ.dump
CONFIRM_RESTORE=1 ./scripts/restore-media.sh backups/webeducation-YYYYMMDDTHHMMSSZ.media.zip
docker compose up -d web proxy
```

`pg_restore --clean` заменяет данные БД. Восстановление media проверяет пути ZIP
перед записью и заменяет файлы в отдельном томе. Перед запуском сделайте
актуальную копию и проверьте совпадение меток; независимые старые скрипты
`backup-db.sh`/`restore-db.sh` не сохраняют файлы. Локальный запуск Compose
проверен; реальное восстановление и запуск на публичном хосте ещё требуют
отдельной проверки.

Локально без Docker используется SQLite:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cd backend
../.venv/bin/python manage.py migrate
../.venv/bin/python manage.py seed_demo
DJANGO_CSRF_TRUSTED_ORIGINS=http://localhost:5173,http://127.0.0.1:5173 ../.venv/bin/python manage.py runserver
```

Для разработки интерфейса в другом терминале:

```bash
cd frontend
npm ci
npm run dev
```

Откройте `http://localhost:5173/`; Vite проксирует `/api/` на локальный Django
порт 8000. Адрес Vite указан в `DJANGO_CSRF_TRUSTED_ORIGINS`, чтобы браузерный
вход не отклонялся проверкой Origin. Команды проверки frontend приведены в
[его README](frontend/README.md).

Тесты:

```bash
cd backend
../.venv/bin/python manage.py test
```

## Вход и проверка сценариев

После локального запуска откройте `http://localhost:5173/login`, войдите под
одной из учётных записей из таблицы выше и проверьте соответствующий кабинет.
Для проверки API доступен healthcheck:

```bash
curl http://localhost:8000/api/v1/health
```

Перед входом браузер получает CSRF cookie через `GET /api/v1/auth/csrf`, затем
передаёт токен в `X-CSRFToken` для изменяющих запросов.

В публичном режиме попытки входа ограничены по IP и логину. Чтобы удалять
устаревшие счётчики из БД, запускайте ежедневно
`docker compose exec -T web python manage.py prune_login_attempts`.

## Порядок разработки

Работа идёт одним агентом по GitFlow: короткая ветка `codex/<задача>` от
`develop`, тесты и аудит, затем PR в `develop`. `main` обновляется через
проверенный релизный PR. Актуальные задачи и границы реализации приведены в
[плане от 25.09](docs/case-compliance-and-task-plan-2026-09-25.md).

## Данные и права

Для разработки и показа используются только синтетические аккаунты и записи, без персональных данных учеников, родителей и педагогов. Учебное содержание организатора получено отдельно от этих аккаунтов. Код проекта распространяется по [лицензии MIT](LICENSE); материалы кейса, брендбук и учебный пакет не становятся автоматически MIT-лицензированными. Оригинальный DOCX добавлен в публичный репозиторий по решению команды и содержит ответы, эталонные решения и тесты с пометкой «скрытый».

## Наблюдаемость API

Каждый API-ответ содержит `X-Request-ID` и то же значение в `meta.request_id`.
Его можно передать во входящем `X-Request-ID`, если это безопасный идентификатор
длиной 8–128 символов (`A-Z`, `a-z`, цифры, `.`, `_`, `-`); иначе сервер создаст
UUID. Django записывает в stdout одну строку на запрос с методом, путём, статусом,
длительностью и `request_id`. Это значение нужно приложить к сообщению об ошибке
при проверке стенда.

## Ветки

`main` — готовые к выпуску версии; `develop` — интеграция; `feature/*` создаются от `develop` и вливаются в неё через PR; `release/*` идёт из `develop` в `main` с обратной синхронизацией; `hotfix/*` идёт из `main` в обе постоянные ветки. Подробнее — в [архитектуре](ARCHITECTURE.md#13-git-и-слияния).
