## Критический порядок задач одного агента

Задачи выполнять строго сверху вниз. Следующая задача не считается начатой,
пока критерий предыдущей не подтверждён тестом или журналом.

### P0-1. Принять и синхронизировать интеграцию

**Состояние:** готово к ревью.

- Дождаться зелёного CI PR #47.
- Смержить PR #47 в `develop` через GitHub.
- После merge выполнить `git fetch --prune`, обновить локальный `develop` и
  проверить, что документация и frontend не потеряны.

**Готово, когда:** `develop` содержит `a3a2a29` или его merge-коммит, все checks
зелёные, рабочее дерево чистое.

### P0-2. Запустить Compose на целевом компьютере

**Состояние:** открыто; Docker отсутствует в текущей среде.

- На компьютере с Docker выполнить `docker compose up --build -d` и `seed_demo`.
- Проверить healthcheck, вход трёх ролей, upload и прямые SPA/API-переходы.
- Проверить повторный старт и сохранность PostgreSQL/media.
- Записать версию Docker, commit SHA, URL, команды и результаты в integration log.

**Готово, когда:** чистый хост поднимает рабочий synthetic demo одной инструкцией.

### P0-3. Зафиксировать контракт официальной Python-сдачи

**Состояние:** открыто; это блокер runner.

- Создание сдачи принимает код и `step_id`, но не принимает stdout/time/memory
  как доверенные результаты.
- Статусы: `queued → checking → accepted|incorrect|error`.
- Сервер выбирает тесты, лимиты и баллы; наружу отдаёт только безопасные
  diagnostics (`passed_tests`, `total_tests`, безопасная причина).
- Локальная кнопка Pyodide остаётся только самопроверкой без баллов.

**Готово, когда:** API-контракт и тесты фиксируют, что поддельные browser results
не могут напрямую создать `accepted`.

### P0-4. Реализовать изолированный Python-runner

**Состояние:** открыто; самый большой технический риск.

- Вынести выполнение из Django/Gunicorn в отдельный worker/container.
- Не давать runner доступ к Docker socket, PostgreSQL, media, секретам и внешней
  сети; использовать непривилегированного пользователя.
- Для каждого запуска создать временную директорию и ограничить время, CPU,
  память, процессы, размер stdout/stderr и файловую систему.
- Добавить очередь и ограничение параллельных запусков; корректно обрабатывать
  timeout, memory limit, output limit, runtime error и worker failure.
- Не импортировать решения из публичного DOCX как trusted tests; серверные тесты
  должны находиться в закрытой конфигурации стенда.

**Готово, когда:** тесты доказывают отказ поддельного stdout, остановку бесконечного
цикла, лимиты памяти/вывода, отсутствие сети и отсутствие доступа к секретам.

### P0-5. Подключить runner к backend и React

**Состояние:** открыто, зависит от P0-3/4.

- Backend создаёт queued submission, передаёт job runner и сохраняет атомарный
  результат с idempotency.
- React отправляет только код, показывает polling и различает incorrect/error/
  checking; локальная самопроверка не меняет баллы.
- Добавить тесты повторной отправки, старой ревизии и недоступного runner.

**Готово, когда:** один Python-шаг проходит `queued → checking → accepted`, а
неверный код и сбой runner показывают разные статусы и не ломают прогресс.

### P0-6. Импортировать пакет 3/9/30

**Состояние:** карта и preflight готовы, запись в БД открыта и зависит от схемы.

- Добавить модульную структуру, паспорт курса и стабильный `source_id` в draft и
  immutable revision, сохранив совместимость синтетического курса.
- Реализовать идемпотентный импорт трёх курсов, девяти модулей и 30 шагов.
- Сохранить многострочные Python-входы, ответы и criteria только в закрытом
  серверном содержимом; ученический API должен отдавать sanitizer-версию.
- Повторный импорт не создаёт дублей и не меняет старые назначения/попытки.

**Готово, когда:** в БД есть 3/9/30, каждый курс проходит правило теории и
контрольного вопроса, а API-тесты подтверждают отсутствие утечки ответов.

### P0-7. Провести полный E2E на импортированном курсе

**Состояние:** локально пройден synthetic E2E, реальный пакет не проверен.

Сценарий: admin публикует и назначает → student проходит теорию/вопрос → локально
проверяет Python → получает официальный серверный результат → сдаёт Scratch,

curator принимает → прогресс обновляется → новая публикация не меняет старое
назначение.

**Готово, когда:** сценарий воспроизводится по README, в журнале есть commit SHA,
время, URL и `request_id`, а персональные данные не записываются.

**Состояние:** Compose и HTTPS-профиль есть, внешний стенд открыт.

- Публиковать только reverse proxy через `cloudflared` на `127.0.0.1:8080`.

- Настроить production secrets, allowed hosts, CSRF origin и persistent volumes.
- Проверить с внешней сети login, polling, upload, скачивание attachment и backup/

**Готово, когда:** новый пользователь открывает URL tunnel и проходит E2E без
ручного доступа к локальным портам.

## Правила GitFlow для одного агента

1. Перед задачей: `git fetch origin --prune`, свежий `develop`, feature-ветка
   `codex/<short-name>`.
2. Один законченный блок — один PR в `develop`; в PR указывать тесты, журнал и
   ограничения. Не пушить напрямую в `main`.
3. Общие модели/миграции и runner менять отдельными PR, чтобы проще откатывать.
4. После merge PR удалять ветку только если она больше не нужна; локальный
   `develop` обновлять сразу.
5. Перед release не смешивать P1 с P0 и не менять публичные материалы
   организатора без отдельного решения команды.
