# Единый план задач

Текущая база — `develop` после PR #54. Ветка
`feature/user-flow-improvements` реализует 11 замечаний ручной проверки
пользовательских сценариев и ожидает PR в `develop`. Результаты аудита,
соответствие кейсу и брендбуку: [аудит 25.09](case-compliance-and-task-plan-2026-09-25.md)
и [отчёт по 11 пунктам](user-flow-remediation.md). Статус API — в
[контракте](api-contract.md), карта страниц — в [user flows](user-flows.md).

## Что готово

- PR #50–#54 влиты в `develop`: Python runner и локальный пример, официальный
  импорт 3 курсов / 9 модулей / 30 шагов, исправленный seed, защита порядка
  прохождения и редактор CodeMirror.
- Текущая feature закрывает пункты 1–11 последней проверки: вход и навигацию,
  каталог и прогресс, беседы, расширение теории Markdown, вложения и отзывы,
  операции с курсами/пользователями/назначениями, профиль ученика.
- На сервере принудительно проверяются права и последовательность шага;
  проверка официального Python-кода остаётся изолированной на сервере, а
  пользовательский ввод для локальной самопроверки остаётся в браузере.
- По брендбуку v1.1 сохранены исходные CSS-токены, шрифты, статусные пары
  «цвет + иконка + подпись», крупная плотность кабинета ученика и разделение
  тона ролей. Владелец подтвердил строгую последовательность, несмотря на
  иллюстративный пример брендбука §06, допускающий следующий шаг во время
  ручной проверки.

## Критический путь до демо

1. **Слить user-flow feature после review.** Автоматические проверки должны
   пройти; ручной E2E должен пройти основные ветки из
   [аудита 11 пунктов](user-flow-remediation.md).
2. **Сквозной E2E на официальном пакете 3/9/30:** администратор публикует и
   назначает курс; ученик проходит по порядку и сдаёт Python/вложения; куратор
   принимает или возвращает с комментарием, отвечает в переписке; прогресс и
   доступ следующего шага обновляются.
3. **Развернуть стенд:** Docker Compose на целевом компьютере, внешний доступ
   только через Cloudflare Tunnel, production secrets и host/CSRF allowlists.
   Проверить загрузку/просмотр файлов и Python runner извне.
4. **Приёмка и release:** проверить восстановление БД и файлов, дополнить
   README фактически подтверждёнными URL и командами, открыть release PR из
   `develop` в `main` после зелёного CI и проверки синтетических данных.

## GitFlow и команды

Каждую следующую задачу начинать с обновлённого `develop`, создавать
`feature/<короткое-имя>`, делать небольшие тематические коммиты и открывать PR
в `develop`. Не вести фичи непосредственно в `main`; в `main` переносить только
проверенный release через PR. Перед началом новой ветки проверить незакоммиченные
изменения и текущие PR, чтобы не затереть чужую работу.

Курсы импортируются командой
`python manage.py import_curriculum --owner admin_demo --publish`; синтетические
роли и назначения создаются через `python manage.py seed_demo`. Контракт runner
и его ограничения описаны в [аудите Python](python-runner-audit-2026-09-25.md).
