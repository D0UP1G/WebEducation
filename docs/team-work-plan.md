## Общий контракт перед параллельными изменениями

DEV-1 фиксирует краткое решение в API-контракте до изменения моделей: как представлены курс → модуль → шаг, паспорт курса, исходный педагогический тип шага и необходимые поля ручной сдачи. Отдельно DEV-1 и DEV-3 согласуют протокол официальной Python-сдачи: браузер передаёт код, но не результаты тестов как источник оценки; сервер запускает код изолированно и возвращает проверенный статус. Локальный Web Worker служит только предварительной самопроверке. DEV-2, DEV-3 и DEV-4 согласуют только нужные поля. Опубликованные ревизии и старые назначения должны оставаться неизменяемыми; миграциями общих моделей владеет DEV-1. Для редактора и импорта использовать один формат данных.

**Решение владельца 24.09:** для публикации каждого курса обязательны теория и контрольный вопрос, как в §04 кейса. Прежнее разрешение курса с одной теорией отменено. DEV-1 обновляет серверную валидацию и тесты; DEV-2 синхронизирует подсказки редактора. Все три курса организатора уже содержат вопросы.

## Порядок и GitFlow

1. Параллельно: DEV-1 пишет контракт схемы и исполнителя, готовит стенд; DEV-2 переносит токены и разделяет локальную/официальную проверку; DEV-3 проверяет типы/вложения и проектирует официальный grading; DEV-4 составляет карту содержания.
2. После контракта: DEV-1 объединяет модели, API и изоляцию в develop; DEV-3 — проверки; DEV-2 — формы и модули; DEV-4 — импорт и E2E.
3. Любая feature-ветка создаётся от свежего develop, один небольшой PR на результат, цель PR — develop. Общие модели и миграции меняет DEV-1; конфликты решать до merge. Тесты и краткий лог проверки обязательны в PR.
4. Стоп-код по кейсу — 26 сентября 2026, 09:00. Сначала принимаются реальные курсы и рабочий URL, затем визуальная полировка и P1. Main обновляется только проверенным release PR.
