# План параллельной работы команды

Статус: предлагаемая декомпозиция для трёх разработчиков и одного дизайнера.
Основана на `ARCHITECTURE.md`, `ROADMAP.md`, `docs/api-contract.md`,
`docs/user-flows.md` и кейсе `keys-obrazovatelnaya-platforma.pdf` из `develop`.

## Что есть в репозитории сейчас

DEV-1 подготовил backend-каркас в `feature/platform-core`: Django/DRF,
PostgreSQL/Compose, общие модели и миграции, auth/CSRF, draft/publish курсов,
назначения, student read API, seed и точки расширения DEV-3. Подробный
фактический статус находится в [backend handoff](backend-handoff.md).

Frontend, submission/review API и настоящий изолированный worker ещё не
реализованы. После вливания каркаса в `develop` DEV-2 и DEV-3 создают свои
feature-ветки от обновлённого `develop`.

Выбранное проектом направление: React + TypeScript, Django + DRF, PostgreSQL,
Docker Compose, сессии Django под одним доменом и отдельный изолированный
обработчик ученического кода. Данные и аккаунты демонстрации — синтетические.

## Общая цель MVP

Один повторяемый сценарий целиком:

1. Администратор создаёт и публикует курс из разных типов шагов и назначает его
   ученику с куратором.
2. Ученик проходит теорию, контрольный вопрос и задачу с точным ответом,
   отправляет Python-задачу и практические Scratch/Minecraft задания.
3. Автоматическая проверка показывает результат в том же сценарии сдачи;
   Scratch/Minecraft ссылка или файл попадает в очередь ручной проверки.
4. Куратор возвращает работу с комментарием, ученик пересдаёт, куратор принимает.
5. Прогресс и объяснимая разбивка баллов обновляются; новая публикация курса не
   меняет старые попытки.

Для Scratch и Minecraft MVP означает инструкции плюс ссылку/файл/снимок и ручную
проверку. Встраивать редакторы или интегрироваться с этими средами не нужно.
Python-код ученика нельзя выполнять в процессе Django или на хосте без изоляции.

## Распределение задач

### DEV-1 — каркас, контракт и ядро платформы

**Владелец:** разработчик 1. Также интегратор backend и координатор миграций.

**Зона файлов:** `backend/config/`, `backend/apps/accounts/`,
`backend/apps/courses/`, `backend/apps/learning/models/`, корневые URL API,
миграции БД, `docker-compose.yml`, `.env.example`, seed-данные и `README.md`.

**Сделать:**

- Зафиксировать API-контракт v1 до интеграции фронтенда и grading-модулей.
- Создать Django/DRF-проект, PostgreSQL и Compose-сервисы с healthcheck;
  подготовить локальный запуск без секретов в Git.
- Реализовать пользователя с ролью, сессионные login/logout/me, CSRF и серверные
  проверки доступа.
- Реализовать Course, CourseRevision, StepRevision и Enrollment. Публикация
  создаёт неизменяемую версию; назначение ученика закрепляет конкретную версию.
- Реализовать draft CRUD, порядок шагов, публикацию, список типов шагов,
  назначения ученика/куратора и чтение назначенного курса/шага учеником.
- Подготовить backend-реестр `type_key`/`schema_version` и общую валидацию
  контента; DEV-3 добавляет проверочные обработчики через согласованный интерфейс.
- Создать синтетические demo-аккаунты и минимальный курс для полного сценария.
- Владеть схемой общих моделей и миграциями: принимать предложения схем от DEV-3,
  проверять порядок миграций и собирать их без конкурирующих изменений.
- Обновить README командами запуска и demo-credentials.

**Критерии готовности:** чистое окружение поднимается одной описанной командой;
три роли входят; администратор может собрать и опубликовать версию курса,
назначить её ученику с куратором; ученик видит только назначенный ему курс и
публичную часть шага; публикация новой версии не меняет прежнее назначение.

### DEV-2 — frontend для трёх ролей

**Владелец:** разработчик 2.

**Зона файлов:** `frontend/` целиком. Не менять backend-контракт напрямую; новые
поля и endpoint'ы предложить DEV-1 до реализации.

**Сделать:**

- Создать React + TypeScript клиент, маршрутизацию по роли, общую оболочку,
  обработку сессии/CSRF и единый API-клиент с типами из контракта.
- Сначала собрать страницы на моках/fixtures, чтобы не ждать backend; затем
  переключить API-клиент на живые endpoint'ы.
- Ученик: мои курсы, обзор курса, следующий шаг, renderer по `type_key`, теория,
  контрольный вопрос, задача с точным ответом, Python, Scratch/Minecraft, отправка ответа/файла/ссылки,
  история попыток, polling статуса, прогресс и вопросы по шагу.
- Куратор: закреплённые ученики и признаки застоя, очередь ручной проверки,
  просмотр контекста/предыдущих попыток, принять/вернуть с комментарием,
  вопросы по шагам.
- Администратор: список курсов, редактор draft и порядка шагов, выбор типа,
  предпросмотр, публикация и назначения.
- Для экранов предусмотреть loading, empty, validation error, server error,
  `pending_review`, `incorrect`, `returned`, `accepted` и `error`; адаптировать ключевой путь под
  ноутбук и мобильный экран.

**Критерии готовности:** все три роли проходят свои части демо-пути; интерфейс
не показывает правильные ответы и скрытые тесты; повторная отправка создаёт
новую попытку; состояние ожидания и комментарий возврата понятны ученику.

### DEV-3 — сдачи, проверки, куратор и прогресс

**Владелец:** разработчик 3.

**Зона файлов:** `backend/apps/grading/`, `backend/apps/mentoring/`,
`backend/apps/progress/`, `backend/worker/`. Реализовывать app-level URL-модули;
корневое подключение URL и общие модели принадлежат DEV-1.

**Сделать:**

- Реализовать endpoint создания и чтения `Submission`, идемпотентность,
  валидацию ответа по типу шага, повторные попытки и историю без перезаписи.
- Проверять `quiz.single_choice` и `answer.exact` на backend.
- Поднять отдельный worker для `algorithm.python`: фиксированная среда, без сети,
  с лимитами времени/CPU/RAM/процессов и размера ввода/вывода; без секретов,
  доступа к БД и Docker-сокета в web/API контейнере. Связать результат с попыткой.
- Для `artifact.scratch` и `artifact.minecraft` принимать допустимый файл/ссылку и
  ставить сдачу в `pending_review`; скачивание файла требует серверной проверки
  доступа и соблюдения лимита размера/формата.
- Реализовать очередь куратора, доступ только к закреплённым ученикам, принятие
  или возврат с комментарием, вопросы/ответы, баллы, прогресс и признаки застоя.
- Держать проверку, принятие, начисление баллов и переходы статусов в доменных
  сервисах; HTTP-обработчики оставлять тонкими.
- Передать DEV-1 предложения по полям общих моделей заранее; не редактировать
  общие модели/миграции параллельно без согласования.

**Критерии готовности:** автоматическая и ручная проверки дают ожидаемые статусы;
возврат требует комментария; принятый шаг начисляет баллы один раз; прогресс
одинаково учитывает авто- и ручную проверку; проверки доступа не позволяют
ученику или куратору читать чужие данные; runner исполняет код вне web-процесса.

### DESIGN-1 — временная дизайн-система и handoff

**Владелец:** дизайнер.

**Зона файлов:** `design/` или Figma-файл и экспортируемая папка `design/`.
Frontend-код и токены внутри `frontend/` принадлежат DEV-2; дизайнер передаёт
готовые значения, а DEV-2 подключает их.

**Сделать:**

- В `develop` нет брендбука, поэтому подготовить временную цельную тему для демо:
  цветовые/типографические/spacing-токены, правила контрастности, кнопки, поля,
  карточки, таблицы, статусы и иконографику.
- Подготовить макеты ключевых экранов: список/обзор курса ученика, шаг и сдача,
  очередь и проверка куратора, список и редактор курса администратора.
- Показать состояния загрузки, пустого списка, ошибки, ожидания проверки,
  возврата и принятой работы; передать короткие правила поведения компонентов.
- Отдать токены в машиночитаемом виде и assets с понятными именами, чтобы DEV-2
  мог подключить их без ручного восстановления размеров и цветов из скриншота.

**Критерии готовности:** DEV-2 может собрать экраны по handoff без догадок;
текст и статусы читаемы для школьников, фокус/контраст различимы, макеты покрывают
все состояния ключевого сценария. Тема не должна задерживать моковый frontend.

## Общие задачи до параллельного кодирования

DEV-1 ведёт короткую фиксацию контракта; остальные участники дают ответы и после
фиксации используют его как границу. Прежние разрывы из `docs/user-flows.md`
уже получили проектные решения в `docs/api-contract.md` и
`docs/case-alignment.md`. Перед реализацией команда подтверждает эти решения:

1. Поиск пользователей по роли, `GET /admin/enrollments` и список назначений.
2. Сводка куратора: список вопросов без ответа и детали закреплённого ученика.
3. История сдач, которую ученик может найти без заранее известного ID.
4. Отметка завершения теории и правило открытия/повторного прохождения шагов.
5. Предпросмотр draft курса до публикации.
6. Формат `GET /student/courses` и способ загрузки прогресса без N+1 запросов.
7. Семантика `incorrect` для неверного автоответа и `error` при сбое runner;
   повторная попытка, серверное вычисление баллов, формула рейтинга и
   обязательность комментария при возврате.

Необязательные для MVP функции можно явно исключить из экранов. Новый endpoint
нельзя считать согласованным только потому, что он появился во frontend mock.

## Порядок параллельной работы и интеграции

| Волна | DEV-1 | DEV-2 | DEV-3 | Дизайнер |
|---|---|---|---|---|
| Старт | Фиксирует спорные пункты API и поднимает backend/DB-каркас | Поднимает frontend shell на моках | Делает worker spike отдельно от Django, предлагает схему сдач/проверки | Делает токены и первые макеты |
| После первого согласованного API | Ядро, публикация, назначения и seed | Подключает auth и ученический путь | Submission API, авто/ручная проверка, вопросы и прогресс | Завершает экраны и состояния |
| Интеграция | Подключает app URL-модули, проверяет миграции, сборку и Compose | Подключает все три ролевых потока и tokens | Интегрирует worker и проверочные сервисы | Поддерживает уточнения, не меняя frontend-код |

Дизайн и frontend на моках, core backend и изолированный runner spike могут идти
параллельно. Подключение сквозных сценариев начинается после согласования API и
первой интеграционной версии схем.

## Git и защита от конфликтов

- Каждый разработчик работает в отдельном worktree и короткой ветке от свежего
  `develop`: `feature/platform-core`, `feature/role-ui`,
  `feature/submission-grading`; дизайнер — `feature/design-handoff`.
- Все feature PR направляются в `develop`; в `main` напрямую не коммитить.
- Владельцы путей указаны выше. `docs/api-contract.md`, корневые backend URL и
  общие модели/миграции меняет DEV-1 после короткого согласования с DEV-2/3.
- DEV-3 сначала открывает маленький PR на независимый runner/interface spike,
  затем app-модули. DEV-2 может открыть UI shell с fixtures до готовности API.
- Любой доменный конфликт возвращает `409 state_conflict`. Перед повтором
  frontend перечитывает ресурс; сервисы DEV-3 используют тот же код для active
  submission и конкурентного review.
- Маленькие PR по вертикальным результатам; синхронизироваться с `develop` перед
  интеграцией. На каждый PR — один быстрый просмотр другого участника.
- Сначала интегрировать запускаемый каркас, auth и один теоретический/тестовый
  шаг; затем auto-check, ручной review, прогресс и остальные типы.

## Обязательный порядок при нехватке времени

1. Запуск проекта и синтетический вход под тремя ролями.
2. Публикация курса и назначение ученика с куратором.
3. Теория, контрольный вопрос, задача с точным ответом и автоматическая
   проверка Python в изолированном worker.
4. Scratch/Minecraft как инструкция и артефакт на ручную проверку.
5. Возврат с комментарием, новая попытка, принятие и обновлённый прогресс.
6. Развёрнутый стенд, README и повторяемая демонстрация.

После ядра брать поиск, сложную аналитику, тонкую полировку редактора и прочие
надстройки. Не брать оплату, CRM, расписание, посещаемость, общий чат,
видеосвязь, продуктовый AI или встроенные редакторы Scratch/Minecraft.

## Критерий командной готовности

Новый участник может поднять приложение по README; демо-пользователь проходит
сквозной путь из раздела «Общая цель MVP»; скрытые тесты не уходят в браузер;
попытки и версия курса сохраняют историю; все роли ограничены своими данными;
команда показывает рабочий URL и может повторить сценарий до стоп-кода кейса.
