# Аудит Python-runner — 25.09.2026

Срез: Python-runner влит в `develop` через PR #50; импорт официальных материалов
добавлен интеграцией PR #51. Runner-проверки ниже фиксируют локальный прогон
25.09, а актуальные общие проверки объединённого дерева записаны в
[плане](case-compliance-and-task-plan-2026-09-25.md).
Цель: выполнить требование §05 кейса — автоматическая проверка алгоритмической
задачи по тестам с быстрым результатом — и разделить локальную самопроверку и
официальный зачёт.

## Что реализовано

- `GET .../python-sample` отдаёт ученику один открытый пример и лимиты.
  Проверка принадлежности назначения и шага сохранена. Закрытый массив
  `content.tests` через этот маршрут не передаётся.
- Pyodide 314.0.7 поставляется из npm-пакета со стендом; сборка копирует
  `.mjs`, `.wasm` и стандартную библиотеку в локальные статические файлы.
  Web Worker выполняет код на примере и показывает вход, ожидаемый и фактический
  вывод, ошибку и время. Самопроверка не создаёт `Submission`.
- Официальный `POST .../submissions` для `algorithm.python` принимает только
  `{ "code": "..." }`. Сериализатор отклоняет `results`, `stdout`,
  `challenge_token` и другие лишние поля.
- Django отправляет код, тесты опубликованной версии и лимиты отдельному
  `runner` по Unix-сокету. Контейнер `runner` не имеет сети, БД, media,
  Docker socket или секретов Django. Файловая система только для чтения;
  `/tmp` — ограниченный tmpfs. Ученический подпроцесс исполняется с UID 10001,
  отдельным временным каталогом и минимальным окружением. Настроены wall-clock,
  CPU, адресное пространство, размер вывода/файла, число процессов и FD.
- Сравнение с эталоном и баллы выполняются на сервере. Ответ содержит только
  число пройденных тестов и безопасную причину: `wrong_answer`,
  `runtime_error`, `time_limit`, `memory_limit`, `output_limit` или
  `environment_error`. Недоступность runner даёт HTTP 503 без записи попытки.
  Если исполнитель занят другой сдачей, второй запрос быстро получает HTTP 503,
  не занимая второй Gunicorn worker ожиданием.
  Повтор по одному `Idempotency-Key` не запускает код снова.

## Сверка с кейсом и открытые риски

- §05: автоматическая серверная оценка реализована в `develop`. Статусы
  `accepted`, `incorrect`, `error` возвращаются синхронно; лимитные причины
  указаны в `safe_diagnostics`. `queued/checking` остаются на будущее.
- §04/09: влитый PR #51 добавил импорт 3 курсов, 9 модулей и 30 шагов;
  чистая SQLite-проверка прошла, а повторный импорт не создаёт новых версий.
  Ученику пока показывается плоский порядок шагов; группы модулей надо вывести
  в интерфейсе и проверить в E2E.
- §10: локальный Compose-контур с браузером и Python проверен. Внешний HTTPS,
  полный сценарий трёх ролей и сохранность данных после перезапуска на целевом
  стенде ещё не проверены.
- Первый CI smoke обнаружил, что supervisor без `DAC_OVERRIDE` не мог войти
  в каталог после передачи его UID 10001. Возможность добавлена только
  управляющему процессу контейнера; повторный CI smoke прошёл. Ученический
  подпроцесс запускается после сброса UID/GID и возможностей.
- Локальный браузерный прогон обнаружил, что Nginx отдавал `pyodide.mjs` как
  `application/octet-stream`; браузер не загружал модуль. HTTP и HTTPS
  конфигурации теперь явно задают MIME для `.mjs`, `.wasm`, `.zip`, `.json` и
  возвращают 404 вместо HTML при отсутствии файла. После исправления свежий
  браузерный сеанс выполнил открытый пример.
- При первом контейнерном прогоне бесконечного кода supervisor получил
  `PermissionError` при остановке процесса UID 10001 и вернул `environment_error`.
  Контейнеру добавлена возможность `KILL`; ученический подпроцесс после смены
  UID/GID должен иметь `CapEff=0`. Контейнерный smoke проверяет сброс
  возможностей и `time_limit`; повторная браузерная сдача вернула именно
  `time_limit`.
- Проверка синхронная, с бюджетом 45 секунд на сдачу. Она занимает один
  Gunicorn worker и удерживает транзакцию до результата; для высокой нагрузки
  потребуется очередь. Валидация задания ограничивает суммарное время тестов
  теми же 45 секундами.
- Локальный Pyodide не гарантирует лимит всей WebAssembly-памяти и даёт только
  обратную связь по открытому примеру. Официальный результат не использует его
  замеры.
- Оригинальный DOCX в публичном Git содержит ответы и эталонные решения.
  Серверный запуск защищает от подмены клиентского stdout, но не от копирования
  опубликованного решения; для устойчивости к подгонке нужны отдельные тесты
  вне публичного пакета.

Следующий шаг — отобразить группы модулей в обзоре курса и провести полный
пользовательский E2E на импортированных данных, затем проверить стенд через
Cloudflare Tunnel. Очередь критериев — в
[плане от 25.09](case-compliance-and-task-plan-2026-09-25.md).

## Повторение на хосте с Docker

```bash
docker compose up --build -d
docker compose exec web python manage.py seed_demo
docker compose run --rm --no-deps runner python smoke.py
docker compose ps
```

Затем войти как `student_demo` и на шаге «Сумма двух чисел» проверить локально
код `a,b=map(int,input().split()); print(a+b)`, отправить его официально и
убедиться, что итог `accepted`/10 баллов. До правильной сдачи можно отправить
неверный код и бесконечный цикл: ожидаются `incorrect` с причинами
`wrong_answer` и `time_limit`. После проверки просмотреть
`docker compose logs runner`; сетевую изоляцию проверяет `smoke.py`, а отсутствие
БД и секретов в mounts/env — `docker compose config`.
