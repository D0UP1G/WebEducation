## Текущее состояние — после PR #14–#20

- PR #14 добавил безопасный `request_id`: входной идентификатор валидируется,
  возвращается в `X-Request-ID` и `meta.request_id`, а запросы логируются с
  методом, путём, статусом и длительностью.
- PR #15 перевёл Nginx на template-механизм и добавил
  `CLIENT_MAX_BODY_SIZE=11m`; точный лимит файла остаётся в Django через
  `MAX_UPLOAD_SIZE=10485760`.
- PR #16 согласовал API-контракт: превышение лимита файла возвращает
  `413 file_too_large`; добавлен регрессионный тест.
- PR #17 добавил защищённые скрипты `scripts/backup-db.sh` и
  `scripts/restore-db.sh`; restore требует явного `CONFIRM_RESTORE=1`.
- PR #20 добавил опциональный HTTPS Compose-профиль: внешний PEM-сертификат,
  HTTP→HTTPS redirect и проверка ключей до старта Nginx.
- На текущей машине прошли 26 backend-тестов, 25 frontend-тестов, system check,
  проверка миграций и production-сборка. Docker/Nginx CLI отсутствуют, поэтому
  Compose, HTTPS и live backup/restore должны быть проверены на стенде.

HTTPS-профиль в `docker-compose.https.yml` и шаблон выбора Nginx
инициализируют только внешний PEM-сертификат и ключ, проверяют их до старта
Nginx и переводят HTTP на HTTPS. Live smoke-тест с реальным доменом и
сертификатом остаётся стендовой проверкой.

## Историческая открытая интеграция DEV-3

На момент этой записи PR #10 `feature/submission-grading` ещё не был влит. Он
не менял общие модели, миграции или корневые URL, поэтому формального конфликта
с DEV-1 не было; сейчас PR #10 и последующие исправления уже в `develop`.

Исторически оставалось архитектурное решение: Python-код
запускается в браузерном Pyodide worker, а сервер принимает результаты тестов.
Такой подход не подтверждает, что код был исполнен, и пользователь может
подделать stdout, duration и memory. На историческом срезе это расходилось с
проектным предложением server-side worker; текущий `ARCHITECTURE.md` фиксирует
браузерный MVP и его границы доверия.

Текущее принятое решение — считать браузерную проверку допустимой только для
учебного MVP без доверенной оценки. Если организаторы потребуют защищённый
зачёт, это будет отдельная фича server-side sandbox до приёмки.

## Правила следующей интеграции

1. Вливать feature PR только в актуальный `develop` после `check`, тестов и
   `makemigrations --check --dry-run`.
2. До изменения `learning/models.py` или миграций описать инвариант, индекс и
   влияние на API в отдельном разделе handoff.
3. После merge обновлять `backend-handoff.md`, `api-contract.md`,
   `team-work-plan.md`, `user-flows.md` и `case-alignment.md` фактическим
   состоянием, не переносить утверждения о готовности из mock UI.
4. При изменении frontend proxy повторять browser CSRF smoke: csrf → login → me
   через порт, на котором опубликован reverse proxy.
