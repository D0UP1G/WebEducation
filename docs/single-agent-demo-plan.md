# Критический план демо на одном хосте

Цель до защиты: поднять проект на одном компьютере/VPS с Docker Compose и
Cloudflare Tunnel, провести один воспроизводимый сценарий трёх ролей и показать
защищённую Python-сдачу. План рассчитан на одного агента и фиксирует порядок,
в котором каждая задача проверяется до перехода к следующей.

## Целевая схема

```text
Интернет → Cloudflare Tunnel → proxy (единственная публичная точка)
                                      ├─ web (Django API + React)
                                      ├─ db (PostgreSQL, только внутренняя сеть)
                                      └─ runner (очередь Python, без Docker socket и секретов)
```

Cloudflare Tunnel не должен проксировать PostgreSQL, Django-порт или runner.
В публичном режиме используются только синтетические аккаунты.

## Порядок реализации

### 1. Стабильный Compose-стенд

- Проверить на хосте `docker compose up --build -d`, `/api/v1/health`, вход
  каждой роли и `seed_demo`.
- Проверить повторный старт без потери PostgreSQL и media.
- Создать `.env` только на хосте: случайный Django secret, пароль PostgreSQL,
  allowed host и HTTPS origin. Секреты не попадают в Git.

### 2. Runner до подключения к UI

Серверная сдача принимает только код и идентификатор задачи. Browser stdout,
время и память больше не являются источником оценки.

- `web` создаёт job со статусом `queued`; `runner` получает его через внутреннюю
  очередь и возвращает безопасный итог.
- Каждый запуск идёт в отдельной временной директории, с закрытым stdout/stderr,
  таймаутом, лимитами CPU, памяти, файлов, процессов и вывода.
- Runner не имеет Docker socket, доступа к media/секретам/БД и внешней сети.
  Параллелизм ограничивается очередью.
- Тесты и ожидаемые ответы выбираются сервером. В API не отдавать эталонный код,
  скрытые тесты или внутренний stderr.

Минимальный контракт: создание сдачи возвращает `queued`, а polling возвращает
`queued|checking|accepted|incorrect|error`; `safe_diagnostics` содержит только
число пройденных тестов и безопасную причину. Статус и баллы вычисляются Django
после результата runner.

### 3. Сквозная приёмка

1. Admin публикует версию и назначает её синтетическому ученику и куратору.
2. Student проходит теорию и вопрос, запускает локальную самопроверку Python.
3. Student отправляет код; runner возвращает неверный результат, затем верный.
4. Student сдаёт Minecraft/Project с обязательными доказательствами.
5. Curator возвращает работу, student пересдаёт, curator принимает.
6. Student видит прогресс; новая публикация не меняет старое назначение.

Каждый шаг записывается в журнал с commit SHA, URL, временем и `request_id`.

### 4. Cloudflare Tunnel и release

- На хосте установить `cloudflared` и направить ingress только на
  `http://127.0.0.1:8080`.
- В `DJANGO_ALLOWED_HOSTS` и `DJANGO_CSRF_TRUSTED_ORIGINS` указать домен tunnel.
- Не открывать наружу 5432, 8000 и runner.
- Проверить с внешней сети логин, upload, polling и скачивание attachment.
- После приёмки открыть `release/*` PR из `develop` в `main`.

## Что отложено

Импорт всех 3/9/30 материалов, модульная модель курса и расширенная аналитика
остаются после рабочего runner и стенда. Они обязательны для полного соответствия
кейсу, но не блокируют первый демонстрационный сценарий.

## Definition of Done

Новый человек запускает Compose, открывает домен Cloudflare и проходит сценарий,
а поддельные stdout/time/memory из браузера не дают официальный зачёт.
