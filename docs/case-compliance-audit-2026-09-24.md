# Актуальный аудит соответствия кейсу

Дата: 24 сентября 2026. Проверяемая база: `develop` на коммите `3345b76`.
Источник требований — [исходный кейс](../keys-obrazovatelnaya-platforma.pdf).
Дополнительно проверены код, [учебный пакет](organizer/basic-curriculum.docx),
[карта импорта](organizer/curriculum-map.json), брендбук и текущие тесты.

## Итог

Функциональное ядро кейса реализовано: есть три роли, сборка и публикация
курсов, автоматическая и ручная проверка, прогресс, вопросы и новые типы
шагов из учебного пакета. Но проект пока нельзя считать полностью принятым
по кейсу: учебный пакет не импортируется в базу, Python не является доверенной
проверкой, а публичный стенд и полный браузерный сценарий не подтверждены.

Локальная проверка текущей ветки:

- backend: 71 тест, успешно;
- frontend: 68 тестов, успешно;
- `check`, проверка миграций, TypeScript и production build — успешно;
- Docker Compose, HTTPS, восстановление PostgreSQL/media и публичный URL — не проверены.

## Недостатки P0 — блокируют строгую приёмку

### P0-01. Учебный пакет не загружен в рабочую базу

Кейс требует работать с реальным учебным пакетом организатора. В репозитории
есть DOCX и `curriculum-map.json` на 3 курса, 9 модулей и 30 шагов, а также
database-independent preflight. Однако в моделях нет `Module`, паспорта курса,
стабильных `source_id` и транзакционного повторяемого импорта. В приложении
остаётся плоская модель `Course` → `DraftStep` и синтетический seed из шести
шагов.

Последствия:

- на демонстрации нельзя открыть реальные три курса из пакета;
- повторный импорт нельзя безопасно выполнить без дублей и потери структуры;
- нельзя доказать сохранение исходной иерархии модулей.

Что сделать: добавить модель/поля модулей и source keys, реализовать
идемпотентный импорт draft-данных, опубликовать импортированные версии и
проверить их через все три роли.

Доказательства: [import-contract](organizer/import-contract.md),
[карта шагов](organizer-step-map.md), `backend/apps/courses/import_plan.py`.

### P0-02. Python-проверка обходится подменой результата

Python запускается в браузере через Pyodide. Сервер принимает присланные
`stdout`, `exit_code`, длительность и память и сравнивает их с ожидаемыми
ответами, но не запускает код сам. Ученик может подменить результаты и получить
принятый шаг без выполнения программы. Общую память WebAssembly и сетевые
вызовы также нельзя надёжно ограничить этим способом.

Что сделать: добавить изолированный серверный runner с ограничениями CPU,
памяти, времени, вывода и закрытыми тестами. Браузерный запуск оставить как
предварительную самопроверку, но официальный статус и баллы вычислять только
по серверному результату. Добавить тест, доказывающий, что поддельный stdout
не даёт баллы.

Доказательства: `backend/apps/grading/services.py`,
`frontend/src/features/student/pythonWorker.ts`.

### P0-03. Нет доказанного публичного стенда и E2E

В репозитории нет проверенного URL. Не подтверждён полный путь:

администратор публикует курс → назначает ученика и куратора → ученик проходит
все типы шагов → куратор возвращает и принимает работу → прогресс меняется →
новая версия курса не меняет старое назначение.

Также не проверены на целевом стенде Docker Compose, HTTPS, SPA-маршруты Nginx,
Pyodide, загрузка файлов, persistent volumes и восстановление БД/media.

Что сделать: поднять стенд, добавить URL и короткий сценарий в README, пройти
его в браузере под всеми ролями и сохранить результаты приёмки.

## Недостатки P1 — существенно мешают эксплуатации

### P1-01. Импорт подготовлен, но не подключён к интерфейсу администратора

Preflight проверяет карту и источник, но не создаёт курсы. Администратор не
может импортировать пакет через UI/API и не видит паспорт, модули и исходные
ключи в редакторе. Сейчас это ручная подготовка для будущего импортёра.

### P1-02. Реальные требования ручных работ не проверены после импорта

API и формы поддерживают `file`, `url`, `explanation` и типы
`artifact.project`, `scratch.numeric_answer`, `quiz.multiple_choice`.
Однако итоговую приёмку обязательных полей и критериев нужно пройти на реально
импортированных шагах. Иначе не доказано, что требования из DOCX корректно
доходят до ученика и куратора после публикации.

### P1-03. Публичный учебный пакет раскрывает эталонные данные

DOCX и карта лежат в открытом Git. В них доступны эталонные решения и данные,
помеченные как скрытые тесты. Это не утечка через ученический API, но такие
тесты нельзя считать секретными и использовать для защищённой оценки.

Что сделать: вынести закрытые тесты/эталоны из публичного репозитория либо
явно обозначить пакет как учебный и не использовать его тесты для официального
рейтинга.

### P1-04. Production-контур требует ручной проверки конфигурации

Production-проверки fail-closed и HTTPS-профиль есть, но дефолтный Compose
содержит локальные значения базы данных и рассчитан на development. Не
подтверждены реальные секреты, домен, сертификаты, secure cookies, backup и
restore на целевом сервере.

Что сделать: запускать публичный стенд только с production env, пройти
`validate_public_environment`, проверить восстановление PostgreSQL и media,
зафиксировать процедуру в README.

### P1-05. Полная визуальная приёмка ещё не проведена

Брендбук и токены интегрированы, рабочие экраны адаптированы, есть компонентные
тесты. Но остаётся стендовая проверка всех трёх ролей, фокуса/контраста,
шрифтов, мобильной ширины и внешней загрузки Google Fonts. Для офлайн-стенда
шрифты нужно разместить локально.

## Недостатки P2 — улучшения после ядра

- UI для просмотра результатов preflight и журнала импорта.
- CSV-отчёты по прогрессу и фильтры очереди куратора.
- Полная браузерная визуальная регрессия для трёх ролей.
- Наблюдаемость ошибок загрузки Pyodide и таймаутов runner.
- Защита веток `main`/`develop` и обязательные CI-проверки на GitHub; наличие
  CI-файла подтверждено, настройки репозитория не проверены.

## Что уже соответствует кейсу

- Три обязательных контура: ученик, куратор, администратор.
- Курсы собираются из расширяемых типов шагов.
- Есть теория и контрольные вопросы.
- Есть Scratch, Minecraft Education, проекты и алгоритмические Python-задачи.
- Есть автоматическая проверка ответов и ручная очередь.
- Куратор может принять или вернуть работу с комментарием.
- Прогресс показывает следующий шаг и разбивку баллов.
- Версия курса фиксируется при назначении.
- Используются синтетические демо-данные.
- В репозитории есть MIT-лицензия, README, CI и backup/restore runbook.

## Минимальный порядок перед защитой

1. Реализовать и проверить импорт 3 курсов / 9 модулей / 30 шагов.
2. Решить вопрос доверенной серверной проверки Python или явно исключить
   Python-баллы из официального зачёта.
3. Развернуть HTTPS-стенд и пройти полный E2E всеми ролями.
4. Проверить импортированные ручные задания, доказательства и критерии.
5. Обновить README проверенным URL, логинами и фактическими ограничениями.

До выполнения первых трёх пунктов проект следует считать функциональным MVP,
но не полностью принятым решением по кейсу.
