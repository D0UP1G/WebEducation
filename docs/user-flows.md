# WebEducation — пользовательские потоки и страницы

Статус: проектное предложение по `ROADMAP.md`, `docs/api-contract.md` и кейсу
хакатона. Пути страниц ниже — предлагаемая карта интерфейса, а не уже
согласованный URL-контракт.

## Цель интерфейса

Показать один сквозной путь: администратор собирает и публикует курс, назначает
его ученику и куратору; ученик проходит шаги и отправляет работу; система
проверяет её автоматически или ставит в очередь куратору; обе роли видят
результат и прогресс.

В демо используются синтетические аккаунты. Регистрации и восстановления пароля
в MVP нет. После входа интерфейс получает роль из `/api/v1/auth/me` и открывает
рабочую область этой роли.

## Общая навигация

1. `/login` — вход по выданным demo-credentials.
2. После входа — переход на стартовую страницу по роли: `/student/courses`,
   `/curator`, `/admin/courses`.
3. В шапке каждой рабочей области — имя, роль и выход.
4. Запросы API проверяют роль и принадлежность данных на сервере; скрытая
   кнопка в интерфейсе не считается контролем доступа.

## Ученик

### Основной путь

`Мои курсы → курс → шаг → ответ или артефакт → результат/комментарий → следующий
шаг`.

| Страница | Что видит ученик | Данные API |
|---|---|---|
| `/student/courses` — мои курсы | Назначенные курсы, процент прохождения, баллы и понятную кнопку продолжения | `GET /student/courses`; список должен содержать enrollment и сводный прогресс либо предусматривать его загрузку |
| `/student/courses/{enrollment_id}` — обзор курса | Название, упорядоченные шаги, состояние каждого шага, баллы, следующий рекомендуемый шаг | `GET /student/enrollments/{id}`, `GET /student/enrollments/{id}/progress` |
| `/student/courses/{enrollment_id}/steps/{step_id}` — шаг | Материал и задание нужного типа, форма ответа/сдачи, баллы и вопросы по этому шагу | `GET /student/enrollments/{id}/steps/{step_id}`, `GET /student/steps/{step_id}/questions` |
| Вкладка/панель «Мои попытки» | Предыдущие отправки, статусы, баллы и комментарии к возврату; действие «Пересдать» | Создание: `POST .../submissions`; детали: `GET /student/submissions/{submission_id}` |

Компонент шага выбирается по `type_key`: теория, тест, Python-задача, Scratch
или Minecraft. Автоматическую проверку ученик видит как «Проверяется» с
обновлением статуса; ручную — как «На проверке у куратора». При возврате видит
причину и может отправить новую попытку. Принятые шаги показывают полученные
баллы и обновляют прогресс.

Вопрос задаётся и читается внутри шага, чтобы он оставался привязанным к
заданию. Общего чата в интерфейсе нет.

### Состояния сдачи для интерфейса

| API-статус | Текст для ученика | Действие |
|---|---|---|
| `queued` | Отправлено | Дождаться начала проверки |
| `checking` | Проверяется автоматически | Обновлять статус с backoff |
| `pending_review` | На проверке у куратора | Ждать решения |
| `accepted` | Принято | Показать баллы и переход к следующему шагу |
| `returned` | Нужно исправить | Показать комментарий и кнопку новой попытки |
| `error` | Не удалось проверить | Показать безопасное объяснение и доступное действие повтора/обращения |

## Куратор

### Основной путь

`Обзор → отстающие ученики или очередь работ → работа ученика → принять/вернуть
с комментарием → обновлённый прогресс`.

| Страница | Что видит куратор | Данные API |
|---|---|---|
| `/curator` — обзор | Сводка ожидающих проверок и учеников с признаками застоя | Сейчас отдельный сводный endpoint не описан |
| `/curator/students` — мои ученики | Только закреплённые ученики, их прогресс и признаки застоя | `GET /curator/students` |
| `/curator/reviews` — очередь | Работы со статусом ожидания ручной проверки, фильтры по курсу/ученику/дате | `GET /curator/reviews?status=pending_review` |
| `/curator/submissions/{submission_id}` — проверка | Ответ, ссылка/файл, тип шага, курс, прошлые попытки и комментарии; формы «Принять» и «Вернуть» | `GET /curator/submissions/{id}`, `POST /curator/submissions/{id}/review` |
| `/curator/questions` — вопросы | Вопросы учеников по шагам, требующие ответа, с переходом к контексту задания | Сейчас есть только `GET /curator/steps/{step_id}/questions` |

При возврате куратор обязательно пишет комментарий. Решение и начисление баллов
проверяет сервер. Куратор не видит чужих учеников и работ.

## Администратор

### Основной путь

`Список курсов → создать/изменить черновик → добавить и упорядочить шаги →
предпросмотр → публикация версии → назначить курс ученику и куратора`.

| Страница | Что видит администратор | Данные API |
|---|---|---|
| `/admin/courses` — курсы | Черновики и опубликованные версии, состояние курса, действие создания | `GET/POST /admin/courses` |
| `/admin/courses/new` или `/admin/courses/{id}/edit` — редактор | Название и описание курса, список шагов, порядок, черновые изменения | `GET/PATCH /admin/courses/{id}`, `POST/PATCH/DELETE .../steps`, `GET /admin/course-types` |
| Предпросмотр курса | Как опубликованный порядок и формулировки будут выглядеть ученику | Нужен read-only preview draft; отдельный endpoint пока не описан |
| Подтверждение публикации | Ошибки валидации по шагам и подтверждение создания неизменяемой версии | `POST /admin/courses/{id}/publish` |
| `/admin/assignments` — назначения | Выбор курса, ученика и куратора; список текущих назначений и их состояние | `POST/PATCH /admin/enrollments`; список назначений и поиск пользователей пока не описаны |

Опубликованный курс отображается как версия только для чтения. Изменения
вносятся в новый draft и публикуются новой версией; существующие назначения и
попытки сохраняют исходную версию.

## Предлагаемая структура интерфейса

- Общие компоненты: вход, шапка, навигация роли, сообщения об ошибках,
  индикаторы загрузки и пустые состояния.
- Ученик: список курсов, индикатор прогресса, содержание курса, рендерер шага
  по типу, форма сдачи, история попыток, контекстные вопросы.
- Куратор: обзор, список закреплённых учеников, фильтруемая очередь,
  просмотр работы, форма решения, вопросы.
- Администратор: список курсов, редактор курса и шага, предпросмотр,
  публикация, назначения.
- Не делать постоянные ветки или отдельные приложения UI по ролям: это один
  клиент с маршрутизацией по роли и общими компонентами.

## Разрывы между кейсом, roadmap и API-контрактом

1. **Minecraft Education.** Кейс включает задания в Minecraft Education, но в
   `ROADMAP.md` тип `artifact.minecraft` отложен до P1. Минимальный путь сдачи
   ссылки или файла с ручной проверкой нужно поднять в P0; прямую интеграцию и
   встроенный редактор можно оставить вне MVP.
2. **Назначения администратора.** Чтобы выбрать ученика и куратора и затем
   показать список назначений, нужны endpoint поиска/списка пользователей по
   ролям и `GET /admin/enrollments` с фильтрами. Сейчас их нет.
3. **Обзор куратора.** Нужен агрегированный список вопросов без ответа, а также
   детали прогресса конкретного закреплённого ученика. Сейчас вопросы доступны
   только в разрезе `step_id`; отдельный endpoint деталей ученика не указан.
4. **История попыток ученика.** После ухода со страницы ученик должен найти
   последнюю сдачу, её статус и комментарий. Нужен список сдач по шагу или
   включение `latest_submission_id`/попыток в ответ шага и прогресса. Один
   `GET /student/submissions/{id}` не помогает найти неизвестный ID.
5. **Теория и навигация шагов.** Контракт описывает чтение шага и общую сдачу,
   но не фиксирует, как ученик отмечает теорию завершённой и можно ли открывать
   шаги повторно/в произвольном порядке. Нужно определить это до реализации.

## Минимальный сценарий показа

1. Администратор публикует курс с теорией, тестом, Python-задачей,
   Scratch- и Minecraft-заданием и назначает ученика с куратором.
2. Ученик проходит авто-проверяемые шаги, отправляет ссылку/файл Scratch или
   Minecraft и видит состояния проверок.
3. Куратор открывает очередь, возвращает одну работу с комментарием; ученик
   исправляет её и отправляет новую попытку.
4. Куратор принимает работу; ученик видит обновлённые баллы и прогресс, а
   куратор — обновлённое состояние ученика.

Это предложение фиксирует видимые пользователю экраны. Детали контента
конкретных заданий, критерии баллов и точный контракт недостающих endpoint'ов
нужно согласовать до разработки соответствующих экранов.
