# WebEducation — пользовательские потоки и страницы

Статус: карта экранов после объединения ядра, frontend и DEV-3 в `develop`.
Текущая приёмка и оставшиеся задачи приведены в
[сверке с кейсом](case-alignment.md).

## Цель интерфейса

Показать один сквозной путь: администратор собирает и публикует курс, назначает
его ученику и куратору; ученик проходит шаги и отправляет работу; система
проверяет её автоматически или ставит в очередь куратору; обе роли видят
результат и прогресс.

В демо используются синтетические аккаунты. Регистрации и восстановления пароля
в MVP нет. После входа интерфейс получает роль из `/api/v1/auth/me` и открывает
рабочую область этой роли.

## Общая навигация

1. `/login` — вход по выданным demo-credentials.
2. После входа — переход на стартовую страницу по роли: `/student/courses`,
   `/curator`, `/admin/courses`.
3. В шапке каждой рабочей области — имя, роль и выход.
4. Запросы API проверяют роль и принадлежность данных на сервере; скрытая
   кнопка в интерфейсе не считается контролем доступа.

## Ученик

### Основной путь

`Мои курсы → курс → шаг → ответ или артефакт → результат/комментарий → следующий
шаг`.

| Страница | Что видит ученик | Данные API |
|---|---|---|
| `/student/courses` — мои курсы | Назначенные курсы, процент прохождения, баллы и понятную кнопку продолжения | `GET /student/courses`; список должен содержать enrollment и сводный прогресс либо предусматривать его загрузку |
| `/student/courses/{enrollment_id}` — обзор курса | Название, упорядоченные шаги, состояние каждого шага, баллы, следующий рекомендуемый шаг | `GET /student/enrollments/{id}`, `GET /student/enrollments/{id}/progress` |
| `/student/courses/{enrollment_id}/steps/{step_id}` — шаг | Материал и задание нужного типа, форма ответа/сдачи, баллы и вопросы по этому шагу | `GET /student/enrollments/{id}/steps/{step_id}`, `GET /student/enrollments/{id}/steps/{step_id}/questions` |
| Вкладка/панель «Мои попытки» | Предыдущие отправки, статусы, баллы и комментарии к возврату; действие «Пересдать» | Список: `GET /student/enrollments/{id}/steps/{step_id}/submissions`; создание: `POST .../submissions`; детали: `GET /student/submissions/{submission_id}` |

Компонент шага выбирается по `type_key`: теория, тест, задача с точным ответом,
Python-задача, Scratch или Minecraft. Во время браузерного запуска Python
ученик видит ожидание, затем получает конечный результат от сервера; ручную
проверку видит как «На проверке у куратора». При возврате видит
причину и может отправить новую попытку. Неверный автоответ показывает
`incorrect`, а технический сбой — `error`; они не смешиваются. Теория отмечается
действием «Прочитал». Принятые шаги показывают полученные баллы и обновляют
процент завершённых шагов и рейтинг по баллам.

Вопрос задаётся и читается внутри шага, чтобы он оставался привязанным к
заданию. Общего чата в интерфейсе нет.

### Состояния сдачи для интерфейса

| API-статус | Текст для ученика | Действие |
|---|---|---|
| `queued` | Отправлено | Дождаться начала проверки |
| `checking` | Проверяется автоматически | Обновлять статус с backoff |
| `pending_review` | На проверке у куратора | Ждать решения |
| `accepted` | Принято | Показать баллы; следующий шаг доступен через обзор курса |
| `incorrect` | Ответ не прошёл проверку | Показать безопасную обратную связь и кнопку новой попытки |
| `returned` | Нужно исправить | Показать комментарий и кнопку новой попытки |
| `error` | Не удалось проверить | Показать безопасное объяснение и доступное действие повтора/обращения |

`queued` и `checking` зарезервированы в модели для возможной асинхронной
проверки. Текущие автоматические сдачи создаются сразу с конечным статусом;
опрос API нужен прежде всего для `pending_review`.

## Куратор

### Основной путь

`Обзор → отстающие ученики или очередь работ → работа ученика → принять/вернуть
с комментарием → обновлённый прогресс`.

| Страница | Что видит куратор | Данные API |
|---|---|---|
| `/curator` — обзор | Сводка ожидающих проверок, вопросов и учеников с признаками застоя | `GET /curator/reviews`, `GET /curator/questions`, `GET /curator/students` |
| `/curator/students` — мои ученики | Только закреплённые ученики, их прогресс и основания сигналов застоя | `GET /curator/students`, `GET /curator/students/{student_id}/enrollments/{enrollment_id}/progress` |
| `/curator/reviews` — очередь | Работы со статусом ожидания ручной проверки | `GET /curator/reviews?status=pending_review` |
| `/curator/submissions/{submission_id}` — проверка | Имя ученика, название шага, ссылка/файл, прошлые попытки и комментарии; формы «Принять» и «Вернуть» | `GET /curator/submissions/{id}`, `POST /curator/submissions/{id}/review` |
| `/curator/questions` — вопросы | Вопросы учеников с названием шага и формой ответа | `GET /curator/questions?status=unanswered` |

При возврате куратор обязательно пишет комментарий. Решение и начисление баллов
проверяет сервер. Куратор не видит чужих учеников и работ.

## Администратор

### Основной путь

`Создать ученика и куратора → список курсов → создать/изменить черновик →
добавить и упорядочить шаги → предпросмотр → публикация версии → назначить курс`.

| Страница | Что видит администратор | Данные API |
|---|---|---|
| `/admin/courses` — курсы | Черновики и опубликованные версии, состояние курса, действие создания | `GET/POST /admin/courses` |
| `/admin/courses/new` или `/admin/courses/{id}/edit` — редактор | Название и описание курса, список шагов, порядок, черновые изменения | `GET/PATCH /admin/courses/{id}`, `POST/PATCH/DELETE .../steps`, `GET /admin/course-types` |
| Предпросмотр курса | Как опубликованный порядок и формулировки будут выглядеть ученику | `GET /admin/courses/{course_id}/preview` |
| Подтверждение публикации | Ошибки валидации по шагам (обязательна только теория) и подтверждение создания неизменяемой версии | `POST /admin/courses/{id}/publish` |
| `/admin/assignments` — назначения | Выбор курса, ученика и куратора; список текущих назначений и их состояние | `GET /admin/users?role=...`, `GET/POST/PATCH /admin/enrollments` |
| `/admin/users` — пользователи | Создание ученика/куратора, список активных и отключённых, управление доступом | `GET/POST /admin/users`, `PATCH /admin/users/{id}` |

Опубликованный курс отображается как версия только для чтения. Изменения
вносятся в новый draft и публикуются новой версией; существующие назначения и
попытки сохраняют исходную версию.

## Структура интерфейса

- Общие компоненты: вход, шапка, навигация роли, сообщения об ошибках,
  индикаторы загрузки и пустые состояния.
- Ученик: список курсов, индикатор прогресса, содержание курса, рендерер шага
  по типу, форма сдачи, история попыток, контекстные вопросы.
- Куратор: обзор, список закреплённых учеников, очередь,
  просмотр работы, форма решения, вопросы.
- Администратор: список курсов, редактор курса и шага, предпросмотр,
  публикация, назначения.
- Не делать постоянные ветки или отдельные приложения UI по ролям: это один
  клиент с маршрутизацией по роли и общими компонентами.

## Состояние согласования

Разрывы по Minecraft Education, назначениям, обзору куратора, истории попыток
и завершению теории закрыты в коде. Полный сценарий на развёрнутом стенде ещё
нужно пройти. Инструкции задания в экране проверки и контекст вопроса куратору
ещё следует добавить. Условия перечислены в
[сверке с кейсом](case-alignment.md).

## Минимальный сценарий показа

1. Администратор публикует курс с теорией, тестом, задачей с ответом, Python-задачей,
   Scratch- и Minecraft-заданием и назначает ученика с куратором.
2. Ученик проходит авто-проверяемые шаги, отправляет ссылку/файл Scratch или
   Minecraft и видит состояния проверок.
3. Куратор открывает очередь, возвращает одну работу с комментарием; ученик
   исправляет её и отправляет новую попытку.
4. Куратор принимает работу; ученик видит обновлённые баллы и прогресс, а
   куратор — обновлённое состояние ученика.

Экраны реализованы для синтетического демонстрационного курса. Сценарий выше
служит чек-листом приёмки на целевом стенде.
