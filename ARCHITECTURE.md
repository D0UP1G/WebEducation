# Архитектура WebEducation

WebEducation — модульный монолит для обучения программированию. Backend на
Django и Django REST Framework хранит курсы, назначения, попытки и роли;
frontend на React и TypeScript показывает рабочие сценарии; Docker Compose
связывает приложение с PostgreSQL, Nginx и изолированным Python-runner.

## Цели и границы

Платформа поддерживает ученика, куратора и администратора. Ученик проходит
назначенный курс и отправляет ответы или работы. Куратор отвечает на вопросы и
проверяет ручные работы. Администратор собирает курс, публикует его версию и
управляет назначениями.

В MVP входят теория, контрольные вопросы, точные ответы, Scratch,
Minecraft Education и Python-задачи с тестами. Также входят автоматическая и
ручная проверка, прогресс и объяснение баллов. Платежи, CRM, расписание,
посещаемость, видеосвязь, общий чат и продуктовые AI-функции не являются частью
системы.

## Компоненты

```text
Browser
  └─ React + TypeScript + Vite
       └─ /api/v1 через Nginx
            └─ Django + DRF ── PostgreSQL
                 ├─ media volume
                 └─ Unix socket ── isolated Python runner
```

- `frontend/` — маршрутизация, страницы ролей, формы, состояние экранов и
  брендовые стили.
- `backend/` — аутентификация, модели, permissions, API, импорт курсов и
  обработчики проверки.
- `runner/` — отдельный процесс для официального исполнения Python-кода. У него
  нет сети, доступ к файловой системе ограничен, а ресурсы процесса ограничены.
- `deploy/nginx/` — раздача собранного frontend и проксирование API/media.
- `docs/organizer/` — исходные материалы и машиночитаемая карта учебного
  пакета.
- `design/` — токены и интерактивный визуальный прототип.

## Модель данных

Главные сущности:

- `User` — аккаунт с одной ролью: `student`, `curator` или `admin`;
- `Course` — логический курс и его состояние;
- `CourseRevision` — неизменяемая опубликованная версия курса или изменяемый
  draft;
- `Module` и `ModuleRevision` — иерархия модулей внутри версии курса;
- `StepRevision` — шаг с `type_key`, схемой, содержимым ученика и закрытыми
  данными проверки;
- `Enrollment` — назначение конкретной версии курса ученику и куратору;
- `Submission` — попытка ответа или ручной сдачи с результатом, баллами и
  историей;
- вопросы и сообщения — переписка ученика с закреплённым куратором в контексте
  назначения и шага.

Опубликованная версия не изменяется. Новые изменения попадают в draft и после
публикации создают новую ревизию. Назначение сохраняет версию курса, поэтому
обновление курса не переписывает историю ученика.

## Типы шагов и проверка

| Тип | Проверка | Результат |
| --- | --- | --- |
| `theory` | завершение чтения | автоматический зачёт |
| `quiz.single_choice` | один вариант | серверный результат |
| `quiz.multiple_choice` | несколько вариантов | серверный результат |
| `answer.exact` | точное значение | серверный результат |
| `scratch.numeric_answer` | числовой ответ | серверный результат |
| `algorithm.python` | тестовые входы и выходы | изолированный runner |
| `artifact.scratch` | ссылка на проект | решение куратора |
| `artifact.minecraft` | файл и ссылка | решение куратора |
| `artifact.project` | файл, ссылка и пояснение по условиям шага | решение куратора |

Локальная кнопка Python запускает открытый пример в браузере для самопроверки.
Она не создаёт попытку и не начисляет баллы. Официальная сдача отправляет на
сервер только код; backend запускает его в runner и сам формирует статус,
диагностику и баллы.

Для ручных работ сервер проверяет обязательные поля шага, тип и размер файла,
сохраняет попытки и ограничивает доступ к файлам владельцем, закреплённым
куратором и администратором. Ученику не возвращаются правильные ответы,
тестовые данные и критерии куратора.

## Основные правила доступа

- API всегда проверяет сессию, роль и принадлежность ресурса; скрытие кнопки во
  frontend не является защитой.
- Ученик видит только свои назначения, шаги, попытки и переписки.
- Куратор видит только закреплённых учеников, их сдачи и вопросы.
- Администратор управляет курсами, пользователями и назначениями.
- Будущие шаги не выдаются через API до выполнения предыдущих. При ожидающей
  ручной проверке текущий шаг остаётся в статусе `pending_review`.
- Снятие назначения скрывает курс из каталога, но не удаляет учебную историю.
- Удаление пользователя отключает вход и сохраняет обезличенную историю.

## Жизненный цикл курса

1. Администратор создаёт или импортирует draft.
2. Редактор проверяет паспорт, модули, порядок шагов и обязательные поля.
3. Администратор публикует ревизию.
4. Опубликованная ревизия назначается ученику и куратору.
5. Ученик проходит шаги, получает автоответ или ждёт ручную проверку.
6. Принятые попытки формируют прогресс и баллы; возврат открывает пересдачу.

Учебный импорт использует `source_id` курсов, модулей и шагов. Повторный импорт
обновляет только записи канонического пакета и не создаёт дубликаты. Подробные
правила находятся в [контракте импорта](docs/organizer/import-contract.md).

## Дизайн и доступность

Рабочий интерфейс использует `design/brand-tokens.css` и правила брендбука:
Onest для интерфейса, JetBrains Mono для кода и чисел, сетку с шагом 4 px,
светлую тему, крупный масштаб для ученика и более плотный — для сотрудников.
Статусы всегда передаются подписью, иконкой и цветом. Визуальные правила и
маршруты экранов собраны в [design/README.md](design/README.md) и
[пользовательских сценариях](docs/user-flows.md).
