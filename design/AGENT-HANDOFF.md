# WebEducation — handoff дизайна для агента

Этот документ помогает продолжить и проверять дизайн без устных пояснений. Он описывает текущий интерфейс и границы между визуальным референсом и рабочим приложением.

## Коротко о направлении

WebEducation — учебная платформа с тремя ролями: ученик, куратор и администратор. Интерфейс строится вокруг следующего понятного действия ученика и быстрых рабочих сценариев сотрудников. Ученические экраны более просторные; staff-экраны плотнее и ориентированы на списки, проверку и управление.

Главное правило: сохранять брендбук, но не копировать из статического макета вымышленные имена, баллы, рейтинги и состояния. Рабочий интерфейс показывает данные API и должен объяснять доступный следующий шаг.

## Материалы и порядок доверия

1. [Оригинальный брендбук v1.1](../docs/organizer/brandbook.pdf) — визуальные ограничения и утверждённые значения.
2. [Рабочие маршруты](../frontend/src/App.tsx), компоненты экранов и API — фактическое поведение, роли и доступные данные.
3. [Рабочие стили приложения](../frontend/src/styles.css) и общий [Layout](../frontend/src/components/Layout.tsx) — актуальная реализация визуальной системы.
4. [Токены для повторного использования](brand-tokens.css) — справочник цветов, шрифтов, отступов и плотности.
5. [Интерактивный HTML-прототип](webeducation-prototype.html) — визуальный ориентир шести экранов, не спецификация API и не источник правды для логики.

Прототип использует демонстрационные данные и автономные действия. Реализация экранов уже перенесена в React и подключена к backend; она намеренно не повторяет макетные цифры и неподдерживаемые API элементы.

## Визуальная система

### Палитра

| Назначение | Значение |
| --- | --- |
| Основной синий / действие | `#3457F0` |
| Синий при наведении | `#2641C9` |
| Светлый синий | `#EAF0FE` |
| Чернильный / основной текст | `#0F172A` |
| Вторичный текст | `#4A546B` |
| Третичный текст | `#7C869C` |
| Фон страницы | `#F4F6FB` |
| Поверхность карточки | `#FFFFFF` |
| Разделитель | `#E1E6F0` |
| Тёмный контекст | `#0B1220`, `#131C30` |
| Экономный янтарный акцент | `#F07A2A`; контрастный текст `#B8520F` |

Семантические статусы: зачтено — зелёный `#17915A`; проверка — фиолетовый `#6E4FE8`; возвращено — янтарный `#B8520F`; ошибка/не пройдены тесты — красный `#D23B3B`; не начато — серый `#5E677D`. Фоновые пары статусов заданы в токенах. Каждый статус отображается вместе с текстовой подписью и иконкой; цвет не является единственным носителем смысла. Красный оставлять для ошибки среды и непрохождения тестов, не использовать как обычный акцент.

Янтарный — редкий акцент (ориентир брендбука: не более 5% площади экрана), а не второй основной цвет. Градиент допустим только в предусмотренном тёмном контексте; текущий пример — тёмный hero следующего шага. Не добавлять градиенты карточкам, обычным кнопкам и фонам страниц.

### Типографика и плотность

- Onest — весь интерфейс. JetBrains Mono — код и табличные/числовые значения, не обычные абзацы.
- Ученик: базовый текст 18 px; заголовок страницы ориентир 36 px, заголовок шага 24 px, вторичный текст 15 px; основная кнопка 56 px высотой, 18 px, радиус 14 px.
- Сотрудники: базовый текст 14 px; h1 28 px; кнопка 40 px высотой, радиус 12 px. Компактные подписи и метаданные допустимы в плотных таблицах, но не уменьшать основной текст ученика ради плотности.
- Пространственная сетка кратна 4 px. Основные радиусы: поля 8 px, рабочие кнопки 12 px, карточки 16 px; pill-статусы — полностью скруглённые.
- Светлая тема — основная. Тёмный цвет используется точечно, а не как альтернативная тема.

### Язык и тон

К ученику обращаемся на «ты», коротко и поддерживающе; к сотрудникам — на «вы», нейтрально и по делу. Не обвинять ученика в ошибке: сообщать, что произошло и что делать дальше. Не добавлять эмодзи. Сигналы темпа и застоя показывать только сотрудникам.

## Поведение и данные — не ломать при редизайне

- Следующий шаг и действие ученика определяются `progress.next_step_id` и `progress.next_action`; не вычислять их заново из цвета или порядка карточек.
- Баллы группируются по фактическим типам шагов. Не добавлять рейтинг группы или другие показатели, которых нет в API.
- Для зачтённого шага показывается источник проверки (автотесты или куратор), если API и тип шага позволяют его определить.
- Ручная проверка не должна превращаться в искусственную блокировку всего курса: показывать «ожидает проверки» и разрешать дальнейшее движение так, как его определяет backend.
- Данные о темпе/застое доступны на экранах сотрудников, не выводить их ученику.
- Состояния загрузки, ошибки, пустого списка, отключённого действия и повторной попытки — часть дизайна, а не временная заглушка.
- В редакторе и проверке сохранять явные подтверждения необратимых/значимых действий и обратную связь о результате.

## Адаптивность и доступность

- Основная ширина контента ограничена примерно 1220 px; рабочие двухколоночные композиции складываются в одну колонку до 980 px.
- До 700 px уменьшить внешние поля и уплотнить карточки. Таблица очереди и горизонтальная карта шагов могут прокручиваться внутри своих областей, не расширяя страницу.
- Сохранять видимый `focus-visible`, текстовые подписи кнопок и статусов, связанные label для полей и семантические заголовки таблиц. Иконки, дублирующие подпись, скрывать от скринридера.
- Минимальная ширина приложения — 320 px. Длинные URL, названия и сообщения не должны ломать сетку.

## Известная оговорка брендбука

В v1.1 есть разница в описании статуса «Не начато»: раздел 03 указывает `#8A93A8`, а таблица токенов раздела 08 — текст `#5E677D` и фон `#F0F2F6`. Текущие CSS-токены приложения используют вариант раздела 08 (`#5E677D`); компонент статуса применяет цвет к подписи и иконке через `currentColor`. Не менять это молча. Если понадобится точное применение двух значений, сохранить читаемую подпись и отдельно согласовать цвет иконки с контрастом.

## Рабочий порядок для следующего агента

1. Сначала открыть оригинальный PDF, этот handoff и нужный React-маршрут; для правки визуала проверять приложение, а не только статичный прототип.
2. Перед изменением понять, есть ли нужное поле/действие в типах и API. Не компенсировать отсутствие данных декоративным демо-контентом; зафиксировать API-пробел отдельно.
3. При изменении палитры, шрифтов или масштабов синхронизировать `design/brand-tokens.css` и `frontend/src/styles.css`, не вводить новую палитру без основания в брендбуке.
4. Сохранить изменения в рамках назначенной области. По текущему GitFlow использовать feature-ветку от `develop` и PR в `develop`; не коммитить напрямую в `main` или `develop`.
5. Проверить из `frontend/`: `npm run typecheck`, `npm test`, `npm run build`. Для визуальных изменений дополнительно проверить широкую и узкую ширину и состояния загрузки/ошибки.

На момент написания handoff статический HTML-прототип и React-экраны существуют параллельно. Если меняется фактическое поведение приложения, обновлять сначала рабочую реализацию и связанные тесты; затем при необходимости синхронизировать прототип и этот документ.
